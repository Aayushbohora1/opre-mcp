# OPRE v1 — Master Development Prompt

## Project Identity

**Name:** OPRE  
**Full Name:** Open Rebuild Engine  
**Repository:** `opre-mcp`  
**Version:** `0.1.0` (initial development release)  
**License:** Apache-2.0  
**Tagline:** Understand. Rebuild. Reimagine.

## 1. Your Role

Act as the lead software architect, senior TypeScript engineer, MCP developer, and testing engineer responsible for building OPRE from the ground up.

You must implement a real, runnable, documented, open-source project. Do not stop at planning, architecture diagrams, pseudocode, placeholder files, or an impressive-looking README.

Inspect the existing repository before making changes. Preserve useful existing code and configuration. If the repository is empty, initialize it properly.

Work incrementally. Implement, run, test, debug, and verify each milestone before proceeding. Do not claim a feature works unless you have tested it.

## 2. Product Vision

OPRE is an open-source, MCP-powered software research and reconstruction engine.

It enables compatible AI agents to investigate existing websites and applications, collect technical information, create a persistent knowledge base, and use that information to build functional alternatives through an incremental, test-driven workflow.

OPRE does not provide its own mandatory AI model. The connected agent performs reasoning and code generation, while OPRE provides tools, research capabilities, persistent project knowledge, task coordination, and validation.

The primary objective is to reconstruct functionality, workflows, and user experiences—not merely copy screenshots or generate superficial interfaces.

Generated applications should use an appropriate implementation and architecture rather than blindly copying the original internals.

## 3. Primary Commands

Design the project around two user-facing workflows:

### `/opreweb <url>`

Start a website reconstruction project.

The workflow should:
1. Validate and record the target URL.
2. Inspect publicly accessible pages and observable behavior.
3. Research available public documentation, source repositories, and relevant technical information.
4. Gather screenshots, page structures, navigation flows, assets, and feature evidence where permitted.
5. Build a structured research knowledge base.
6. Create an implementation plan ordered by dependencies and priority.
7. Let the connected AI agent implement the essential functionality first.
8. Run the generated website locally in a browser.
9. Test implemented workflows, record failures, and update the knowledge base.
10. Continue implementation incrementally until the defined requirements are satisfied or a clear stopping condition is reached.

### `/opreapp <target>`

Start an application reconstruction project that produces a web-based alternative.

Research may include:
- Official documentation and publicly available technical information.
- Public source code and dependency metadata.
- Application manifests, resources, and assets where available.
- Authorized APK inspection and decompilation.
- Observable application behavior and screenshots.
- Publicly documented APIs and permitted network behavior.

The output of this workflow is a browser-based implementation, not an Android APK.

Record inaccessible components, uncertain behavior, and server-side dependencies explicitly. Do not pretend that decompilation reveals code or functionality that cannot be observed.

Important: slash commands are not a universal MCP feature. Implement OPRE's underlying functionality as reusable MCP tools and provide agent-specific slash-command integrations or instructions where supported. Do not assume every agent supports the same command syntax.

## 4. Technology Stack

Use the following defaults unless the existing repository has a justified, compatible alternative:

- TypeScript with strict type checking.
- Node.js with a currently supported LTS release.
- The official TypeScript MCP SDK.
- Zod or equivalent runtime schema validation.
- Playwright for browser inspection and testing.
- Vitest for unit and integration testing.
- Markdown and JSON for persistent project documents.
- npm workspaces only if the repository genuinely benefits from multiple packages.
- ESLint and Prettier for code quality and consistent formatting.

Use stable, compatible dependencies and lock their resolved versions. Do not invent package names or API methods. Consult installed package types and official documentation when needed.

Keep the initial implementation small and modular. Avoid unnecessary frameworks, microservices, and complex infrastructure.

## 5. Core Architecture

Separate the following modules so each can be developed and tested independently.

### A. MCP Server

Expose clearly defined tools for project management, research, knowledge retrieval, planning, building, execution, and validation.

The MCP server must:
- Use structured input schemas.
- Validate inputs and return useful error messages.
- Support progress reporting where appropriate.
- Return concise, structured results.
- Keep large artifacts outside tool responses.
- Never require the agent to receive the entire research database.
- Support project identification so separate projects cannot accidentally share their state.
- Provide clear descriptions that explain when each tool should be used.

Implement stdio transport first for local compatibility. Keep the design extensible for other transports without implementing unnecessary infrastructure in v1.

### B. Research Engine

Build a source-aware research pipeline.

For websites, gather:
- Page inventory and navigation structure.
- Screenshots and relevant visual evidence.
- Forms, buttons, interactive elements, and observable workflows.
- Responsive behavior at selected viewport sizes.
- Publicly accessible metadata and assets.
- Public documentation and technical references.
- Available source-code and dependency information.

For applications, gather available documentation, manifests, resources, package metadata, source code, and authorized binary-analysis findings.

Provide a configurable web-search adapter. Do not assume MCP automatically supplies web search. If no provider is configured, return a clear error or support a limited, documented alternative rather than fabricating search results.

Store every important finding with provenance:
- Finding identifier.
- Source type and reference.
- Collection timestamp.
- Supporting evidence.
- Confidence level.
- Verification status.
- Relevant feature or workflow.
- Known limitations.

Distinguish observed facts, source-derived facts, and hypotheses.

Do not bypass authentication, paywalls, access controls, anti-bot protections, or other restrictions. Do not collect secrets or expose credentials. Only analyze software and resources that the user owns or is authorized to inspect.

### C. Persistent Knowledge Base

Create a local project directory for each OPRE project.

Use a structure similar to:

opre-project/
  opre.json
  research/
    overview.md
    sources.json
    findings.json
    pages.json
    architecture.md
  knowledge/
    features.json
    workflows/
    requirements.md
    decisions.md
    uncertainties.md
  planning/
    implementation-plan.md
    tasks.json
  artifacts/
    screenshots/
    reports/
  validation/
    test-results.json
    known-gaps.md
  generated-app/

Adapt this structure where useful, but preserve the separation between research, knowledge, planning, generated code, and validation.

The knowledge base must:
- Persist between agent sessions.
- Support incremental updates.
- Track feature and task status.
- Preserve evidence references.
- Record decisions and unresolved questions.
- Avoid duplicating large documents.
- Support searching and retrieving relevant information.
- Never overwrite user changes without an explicit, safe operation.

Do not store the complete research corpus in a system prompt or a single massive context document.

### D. Context Preservation Engine

This is a core OPRE requirement, not an optional optimization.

The connected agent may already have a long conversation, project instructions, and implementation decisions. OPRE must minimize the extra context it introduces.

Implement the following rules:

1. Never return the entire knowledge base unless explicitly requested.
2. Return only information relevant to the current feature or task.
3. Use bounded result sizes and pagination.
4. Return document identifiers, paths, and concise summaries instead of full file contents whenever possible.
5. Allow the agent to request specific excerpts or evidence on demand.
6. Track task progress and persistent decisions outside the conversation.
7. Avoid repeatedly returning unchanged summaries.
8. Avoid injecting the full research corpus into agent instructions.
9. Provide configurable response-size limits and deterministic truncation behavior.
10. Never claim to control the host agent's context window, history, or compaction.

Create retrieval tools such as:
- `opre.search_knowledge`
- `opre.get_feature`
- `opre.get_evidence`
- `opre.get_task`
- `opre.get_document_excerpt`
- `opre.get_project_status`

Each tool should return only the fields needed to perform its task.

Do not use arbitrary, unverified token estimates as guarantees. If token counting is not implemented for a specific model, use conservative character or byte limits and describe them accurately.

### E. Build Engine

The connected AI agent is responsible for reasoning and generating implementation code.

OPRE should provide the agent with:
- A prioritized task.
- Acceptance criteria.
- Relevant feature requirements.
- Relevant research evidence.
- Dependencies and existing implementation decisions.
- Required validation steps.

Implement a workflow in which the agent:
1. Selects or receives the next task.
2. Retrieves only the necessary context.
3. Implements one logical feature or small group of related changes.
4. Runs relevant tests.
5. Records the result and any discovered gaps.
6. Updates the task status and project knowledge.
7. Moves to the next task only when dependencies and acceptance criteria permit.

Do not attempt to build the entire application in one giant code-generation operation.

Prioritize a minimal working foundation, then expand through verified increments.

### F. Browser Runner and Validation Engine

Generated websites must be runnable locally and testable through Playwright.

Implement capabilities to:
- Start a configured development server.
- Check whether it starts successfully.
- Open the generated application in a browser.
- Capture screenshots.
- Execute defined browser workflows.
- Check navigation, form interactions, and expected UI states.
- Record console errors and failed requests where available.
- Compare observed results with acceptance criteria.
- Produce structured validation reports.
- Track implemented, failed, blocked, and unverified features.

Use explicit configuration for development commands and ports.

Do not execute arbitrary shell commands or untrusted project scripts without appropriate safeguards. Keep execution within the configured project workspace and provide a clear mechanism for user approval of risky operations.

Do not claim complete equivalence based solely on visual similarity or passing a small number of tests.

### G. Feedback Loop

Connect validation back to the knowledge base.

When a test fails:
1. Record the failure and relevant evidence.
2. Identify the affected feature and task.
3. Update the known-gaps report.
4. Make relevant information retrievable to the agent.
5. Let the agent correct the implementation.
6. Rerun the relevant tests.
7. Record the new outcome.

Avoid endless automatic retries. Use configurable iteration limits and stop when blocked, when approval is required, or when further attempts are unlikely to help.

## 7. Security and Project Isolation

Treat webpages, repository content, downloaded files, source code, and research results as untrusted data.

A target website may contain malicious instructions intended to manipulate the AI agent. Such content must be treated as evidence, not as trusted system instructions.

Implement safeguards for:
- Prompt injection in researched content.
- Path traversal and writes outside the project directory.
- Unsafe URL schemes and server-side request forgery.
- Access to local files and sensitive environment variables.
- Arbitrary command execution.
- Dependency installation and untrusted build scripts.
- Secret leakage in logs and reports.
- Cross-project data contamination.
- Accidental overwriting or deletion of user data.

Validate URLs and restrict requests to permitted destinations. Handle redirects carefully and prevent access to local or private network services unless explicitly authorized and safely configured.

Provide clear user approval boundaries for destructive or security-sensitive actions.

Keep the tool's permissions as narrow as possible. Do not add stealth, credential theft, unauthorized access, or security-control bypass features.

## 9. Development Milestones

Implement the project in the following order.

### Milestone 1: Working Foundation
- Initialize TypeScript and Node.js configuration.
- Configure the MCP server and stdio transport.
- Implement schema validation and error handling.
- Implement project creation and status retrieval.
- Create the persistent project directory structure.
- Add tests and a basic README.
- Verify the server can start and a client can successfully call its tools.

### Milestone 2: Context-Safe Knowledge
- Implement feature and evidence storage.
- Add bounded knowledge search and excerpt retrieval.
- Add pagination and configurable response limits.
- Add task persistence and status updates.
- Test that large research datasets never leak into default responses.

### Milestone 3: Website Research
- Implement authorized browser inspection using Playwright.
- Build page inventories and basic interaction discovery.
- Integrate configurable web search.
- Store evidence and source references.
- Generate the first useful research report.

### Milestone 4: Planning and Incremental Building
- Convert research into structured features and tasks.
- Prepare small, task-specific build contexts.
- Record implementation results.
- Preserve progress between sessions.

### Milestone 5: Execution and Validation
- Add a safe local web-app runner.
- Implement browser-based acceptance tests.
- Store screenshots and structured test results.
- Add the research-to-build feedback loop.

### Milestone 6: `/opreapp`
- Add authorized application-package inspection.
- Collect manifests, resources, metadata, and accessible code-analysis results.
- Produce a web-reconstruction plan.
- Reuse the same knowledge, build, and validation infrastructure.

Do not attempt all milestones in one unverified pass. Complete and test each milestone before expanding.

## 10. Definition of Done for the Initial Release

The initial working release must demonstrate that:

- An MCP-compatible client can connect to OPRE.
- A user can create and resume an isolated project.
- Research data persists on disk.
- The agent can search for specific information without loading the entire database.
- Tool responses respect configured size limits.
- Tasks and implementation decisions survive server restarts.
- Website research can generate a structured, evidence-backed report.
- The agent can retrieve context for a specific implementation task.
- A generated web application can be launched and tested locally.
- Test failures are stored and made available for subsequent iterations.
- Security-sensitive operations are constrained and documented.
- Setup instructions are sufficient for another developer to reproduce the workflow.

Clearly identify incomplete features. Do not label a milestone complete based on compilation alone.

## 11. Working Rules

- Start by inspecting the repository and available development environment.
- Explain the proposed implementation briefly, then begin coding.
- Prefer working code over extensive planning.
- Keep modules small, typed, testable, and well documented.
- Run the relevant tests after each meaningful change.
- Fix regressions before proceeding.
- Do not silently replace existing configurations.
- Do not introduce unnecessary abstractions.
- Do not generate fake research, fake test results, or fabricated citations.
- Ask for clarification only when a decision materially blocks progress.
- If external access, credentials, or an unavailable service prevents implementation, explain the limitation and provide a useful local fallback.
- Maintain a concise development log and identify the next incomplete milestone.

## Final Instruction

Begin with Milestone 1.

Inspect the repository, establish the smallest sound architecture, implement the working MCP foundation and project manager, write tests, run them, fix failures, and document how to launch and connect to OPRE.

Continue through the milestones when the environment and available tools permit. Prioritize context safety, evidence quality, persistent state, and a reproducible end-to-end workflow over feature count.

The goal is to build OPRE into a dependable open-source software reconstruction engine—not merely another AI wrapper around a large prompt.
